# The Solar Century: architecture and detailed conventions

Reference for Claude, read **only the section a task needs** (it is long on purpose so `CLAUDE.md` can stay short). The design itself is in `GDD.html`; the rules for working are in `CLAUDE.md`.

In `index.html`, the main script is split into sections that start with a comment line `/* ===== NAME ===== */`. Search for `===== ` to find them (GAME DATA, STATE AND COLONISTS, POWER CONSTRUCTION AND RESEARCH, STARPORT AND STARSHIPS, SURVEY AND COLONISATION, MISSIONS AND THE GAME CLOCK, FORMATTING ICONS AND THE RESOURCES BAR, LOCATIONS, COLONIES AND DATABASE OVERVIEWS, STARSHIPS OVERVIEW DATA, LOCATION SCENES, MAP, SCREENS AND RENDER, INPUT, MODES, CONFIGURATIONS, EDITOR).

## Architecture of `index.html`

- **Game logic and UI are kept apart** (so the rules can be ported, for example to C#). The sections from GAME DATA to MISSIONS AND THE GAME CLOCK only read and change `S`: they never touch the page, call `render()`, open dialogs or read the URL. Player actions (`build`, `assign`, `launch`, `svSend`...) just change `S`; buttons run them through `act(fn, ...args)`, which redraws afterwards (also the Starships list listener). Confirmations (recycling a ship) are asked by the UI before calling the action. Game over sets `S.over` and the message in `S.end`; `render()` shows the end dialog once per game (`endShown`). Messages go to `S.log` through `say()`. HTML builders (`svHtml`, `orbHtml`, `modRows`...) live in SCREENS AND RENDER.
- **UI state** `U` (open screen `U.screen`, location on view `U.loc`, map zoom `U.view.z`) is created by `initUI()`, next to `init()`, and is not part of the game; `?loc=` and `?z=` are read there. Other UI-only globals (`svSel`, `dbTab`, `shipTab`, `edTab`...) stay out of `S` too.
- **State** `S` is created by `init()`. One tick is one game hour (`tick()`). The calendar is the real Gregorian one (`dim()` days per month, leap years included, so 2100 is not a leap year; `wday()` gives the weekday): the game starts on Fri 2100-01-01 and `DEADLINE` is 2200. Rates and durations still use 720 hours as one "game month". Speeds are set by `data-sp` buttons.
- **Game data** lives in plain objects: `B` buildings, `T` technologies, `M` missions, `SHIP` probe cost, `STAFF` job needs per building, `CREW` crew per mission, `COL` colonist constants (starting number, full-crew bonus and `COL.rates`: air, water and food per colonist per month for each lifeform; `needs()` turns them into the colony's monthly consumption using the lifeform of the Moonbase, `LIFE`/`LOCD.life`), `PORT` Starport berths, `LOCD` locations (planets and moons, seeded from `LOCS` and `LOCRES`). `DATA` groups them and `DEF` is a JSON snapshot of the defaults.
- **Configurations and the Editor:** `applyData(d)` replaces the data in place, merging missing parts from `DEF`. Named configurations are stored in `localStorage` under `solar-century-configs`. The built-in Default is read-only. Any new game data object must be added to `DATA` (not to `OKEYS`, so older saved configurations still load) and get an Editor tab or section.
- **Stage:** `#game` is a fixed 1920x1080 `.stage`, scaled by `fit()` (or `?scale=`). `#scene` is the full-stage background (hotspots hidden when an overview is open); `header` and `main>.win` are absolutely positioned floating UI. Media queries no longer apply to the game.
- **Location scenes:** `SCENES` (one entry per location key in `LOCD`) describes a placeholder scene drawn with CSS shapes on the 1920x1080 stage: sky, stars, sun, parent planet or rocks, ground. `sceneHtml(key)` builds it; the main screen draws the one for `U.loc` (always `moon` for now; `?loc=mars` in the URL starts the game at another location for testing) and hides the Moonbase hotspots away from the Moon. Each Database location entry shows a 320x180 preview. `SCENES` is visual only, so it is not in `DATA` or the Editor. Real art replaces these later.
- **The map:** the main screen has seven zoom levels, kept in `U.view.z` with the selected location in `U.loc`: 1 Solar System, 2 Outer Planets, 3 Middle Planets, 4 Inner Planets (regions as in `COLPAGES`; `REGLV` gives each region's level), 5 planetary system (planet plus its moons), 6 orbit of a location (big globe, orbit ring, orbiting marker), 7 the location's main screen (`SCENES`). Levels 1 to 6 are drawn by `mapHtml()` into `#mapbg` (full stage, behind the UI). **Levels 1 to 4 are to scale around the Sun** (`LVL` gives pixels per AU: 7.5, 10.4, 47 and 160, plus the Sun size and a base planet size; planet sizes are only ranked by real radius, `RKM`, and are exaggerated but not too much, `rpx()`). Orbits are real ellipses with the Sun at a focus (`orbitSvg()`, from `LOCD` `a`, `ecc` and the longitude of perihelion in `EPH`); planets are placed on their real Kepler orbit for the game date (`kepler()`, `EPH` holds the J2000 mean longitude and perihelion longitude, `daysJ()` the days since J2000), so the real positions of 2100 show. **The map plane is tilted `TILT` (now 40, was 23) degrees towards the viewer** (levels 1 to 6): y is flattened by `TY` = cos(TILT) (orbit ellipses, zone rings, belts, moon rings and positions), bodies stay round sprites, nearer ones (lower on screen) get a higher z-index and are slightly bigger (`put()` in `updateOrbits()`), and **see-through**: a body partly hidden behind a nearer one (including the Sun, `data-rad` holds each radius) fades to 30% opacity. The asteroid belt (2.1 to 3.3 AU) and the Kuiper belt (30 to 50 AU, levels 1 and 2) are dot bands. A level draws only the bodies of its own region (level 1 draws the Middle and Outer ones; the inner planets sit under the Sun there, so the Inner zone stands for them). **Level 5** places moons at their real orbit radii, scaled so the outermost one sits 430 px out (`SYSR`; Saturn's moons use a compressed exponent, `SYSG`, so the inner ones clear the globe); the planet globe is capped so it does not touch the innermost moon. Level 5 and 6 bodies use `PLR`, `MR` and `GLOBE`; moons are circular with an arbitrary starting phase. Orbital periods are the real ones from `LOCD[k].per` through `PER(k)` (`RETRO` marks Triton as backwards); everything turns counter-clockwise seen from the north. `updateOrbits()` runs every animation frame and moves each element from `data-kep` (planets), `data-per`, `data-r` and `data-ph` (moons), so the HTML itself never changes between ticks. At level 1 the space around the orbits is split into three concentric zones (`ZONES`, in AU: Inner up to 4.1, Middle up to 14, Outer up to 56): hovering anywhere in a zone highlights it with its name, and clicking zooms to that region's level. Clicking a body at level 1 opens its region, at levels 2 to 4 its system, then its orbit, then its surface. The mouse wheel steps one level (up in, down out); zooming in from level 1 goes to the region under the pointer (else Outer) and then steps Outer, Middle, Inner; from a region level a body under the pointer opens its system, else the next level in; zooming out from a system goes to its own region. It is throttled and ignored over floating windows or while an overview is open. The zoom bar at the bottom jumps between levels; the Moonbase button returns to level 7 on the Moon. The colony marker is an orange ring (on a planet if one of its moons has a colony; at level 1 around the Sun for the inner region). `?z=1..7` and `?loc=` in the URL start the game at another view for testing. Off level 7 (or off the Moon) the hotspots and the Moonbase panel are hidden.
- **Rendering:** `render()` rebuilds screens from `S`, `U` and the data. `set(id, html)` only writes the DOM when the HTML string changed, which keeps hover tooltips and focus alive between ticks. Screens are the `SCR` list, shown by `go(name)`.
- **Icons:** inline SVGs in the `ICON` object, drawn in a 16x16 box, used through `ico(key)`. Reuse existing icons before adding new ones.
- `refreshD()` rebuilds building descriptions from data, so do not hard-code them.
- **Themes:** the hamburger menu (`#menu`, dialog `#dmenu`) has the theme switch. It sets `data-theme` on `<html>` (light tokens in `:root[data-theme="light"]`, else the system preference) and stores it in `localStorage` under `solar-century-theme`, a key `GDD.html` shares. A small script in `<head>` applies it before the page draws.

## UI conventions in detail

- Top controls sit on the page background (no bar): the Moonbase button, then the Colonies, Starships, Technology, Mission Control and Database overview buttons touching each other (no space between them) 12px after Moonbase (the header is a CSS grid whose first column is as wide as its widest item; since the Resources bar went to two rows the button group is wider than the bar and sticks out about 20px past its right end, which the owner accepted), on the left, the date and a hamburger menu on the right, and the grouped icon clock below.
- The date is bold 20px Jura with slightly wider spacing; the weekday and the time sit stacked in small 12px text at its right (so the weekday fits). Its left edge must never go past the left of the clock's pause button (even for the widest dates, such as 2199-12-28 00:00): recheck this if its size or spacing changes.
- The colony name (`#colname`, now "Moonbase – Mare Tranquillitatis") sits alone in the centre of the stage at the top, in orange, always visible during the game and not inside any panel. The colonists chip (`#pop`) moved into the top of the Moonbase panel.
- Every floating screen except the Moonbase panel has its title centred in a 75px title bar, at the colony name's size (26px), and a close button at the right of it (`.xb`, the Main menu button's size, 42x35 with a 20px icon, tinted red) (added in code to each `h2`, returns to `base`). These screens start just below the clock (top 95px), so the Resources and Research points bars float over their top-left corner. The header box ignores the pointer (`pointer-events:none`, its children take it back) so it does not block the close button under it.
- In every floating screen the title bar (with its close button) and the filters or tabs (the `.sticky` blocks: Colonies pager, Starships pager and type filters, Technology category filters, Database tabs, Log tabs) stay pinned when scrolling; only the content scrolls. New screens with filters must wrap them in `.sticky` (it sticks 75px below the top, under the title bar).
- Overview screens (Colonies, Starships) use a pager: a centred orange title with fixed arrow buttons at the far left and right. Colonies has three named, fixed pages (Inner, Middle and Outer Planets). Starships is the "Moon Fleet", 12 per page, filtered by the five ship type buttons.
- A Resources bar sits on the second line of the top bar (left-aligned with the Moonbase button; the clock is at the right of that line), and the Research points bar sits on a third line right below it, as wide as the Moonbase button (106px) with the same treatment as the categories (big dimmed flask behind the centred number, 100px hover area). The Resources bar has two rows of nine resources (`RROWS`: Volatiles and Metals above; Minerals, Rare metals and Manufactured below), each quantity in a fixed 44px slot (three digits, then `n3()` switches to k and M, so "999k" fits). Only the top row stretches, just enough to end level with the bottom row; sections otherwise take their natural width. It is one merged bar divided by dashed lines, with the category icon (28px, full opacity) in a 32px box at the section's left edge (darker background, solid line on its right, like the starship part chips; numbers start 38px in; the Research points flask is boxed the same way, with its number centred in the rest of its bar) behind the numbers and clipped to the bar, then each resource as just its quantity in bold (no icon), separated by "·", in the fixed `CAT` order. A quantity is green if growing, normal text colour if stale, red if diminishing (`resRate()`). Tooltips: the category name over the icon; over a resource, its icon, name and the net growth per day in smaller text (the Research points follow the same colour and tooltip rules). The owner is refining the top bar step by step.

## Game systems in code

- The Starport is a Moonbase screen, not a building. It starts with 1 berth and expands to 8, one berth at a time, through the Construction queue. Probes built in the Shipyard are berthed automatically, and a ship away on a mission keeps its berth.
- Colonists take jobs (Labourers, Scientists, Technicians, Builders, Crew) with a minimum to run and a boost when fully manned. They consume water, food (made by Hydroponics) and a lifeform-specific gas; without any of them a colonist dies each day.
- Technologies have a category (`cat`, from `TCATS`: Colonization, Energy, Mining, Manufacturing, Life Support, Starships, Weapons). The categories are the filters of the Technology overview (same button style as the Starships type filters).
- **Colonisation:** every location has in `LOCD` (editable in the Editor): `adiff` analysis difficulty (0 to 1), `alen` analysis length in days and real orbital data (`a` AU from the Sun for planets and the belt, `ak` thousand km from its planet for moons, `ecc`, `per` period in days; seeded from `LOCORB`). The probe trip is not stored: it is computed from the real positions of the bodies on the date (`tripDays(from,to,t0)`, cached per day by `tripFrom`; `tripD(k)` is from `HOME`, the Moon). The probe leaves at day `t0` and flies straight at `SURVEY.dpa` days per AU (1946, so the Moon to Earth takes 5 days with the simplest drive) towards where the target will be: the trip is the first time T when speed × T reaches the distance to the target's `kepler()` position at `t0+T`. So trips change with the date (launch windows) and the Database shows the trip "if launched today" and the distance today (`distNow`). The trip is fixed at launch; a recall computes the way back from the current date (`tripFrom(k,HOME)`). Inside one planetary system (Moon to Earth) the real orbit distance (`distAU`) is used; moons of a planet share its heliocentric position; the belt uses Ceres (`EPH.belt`). Durations are shown by `lapse(days)`: hours under a day, days under a month, then months and days, then years, months and days (month = 365.25/12 days). `SURVEY` holds the shared constants (probe cost per flight, failure factor, technology cost formula, colonisation module cost and time). Flow: send a probe (`svSend`, from the orbit view panel `#orbpanel` or Flight plans; it is an unmanned `S.out` entry with `k:'survey'`, `ph` fly, orbit, scan or back) → in orbit, "Start analysis" (`svStart`) → after `alen` days it succeeds with chance `1 - adiff × SURVEY.fail` (`svTick`; a failure leaves the probe in orbit to retry) → success sets `S.sv[loc].done` and unlocks the generated technology `col_<loc>` ("Colonise X", category Colonization, cost `rpBase × (1 + rpDiff × adiff) × (1 + alen / rpLen)` points, rebuilt by `genTechs()` inside `refreshD()`; generated techs have `gen:1`, are hidden from the Editor and the Database, and only show (`visT`) once the analysis succeeded) → once researched, Construction offers a colonisation module (`buildMod`, queue key `colmod:<loc>`) → when built, `S.mods[loc]=1`. Launching the module and creating the colony are not implemented yet. The starting colony (Moon) counts as surveyed, researched and built.
- Research needs a staffed Science Lab. A running project cuts passive research points to 25%.
- Locations are listed with what each can provide (placeholder numbers) but only the Moonbase exists and produces.

## GDD internals

- `GDD.html` draws its tables from a block between `SYNC:BEGIN` and `SYNC:END` that `node tools/sync-gdd.js` copies verbatim from `index.html` (the constants listed in its `NAMES`, the starting state from `init()` as `START_STATE`) plus a `SYNC` line with the revision number, date and history from git (written only when the GDD differs from the last commit or its data changes, so syncing never churns). A new game data object the GDD should show: add its name to `NAMES`, then use it in the GDD's `fill()`.
- Numbers inside the GDD prose use `<span data-val="expression">` (for example `SURVEY.dpa`, `PORT.t/24`) and costs use `<span data-cost="expression">`; they are filled from the synced data, so prose never repeats a number by hand.
- GDD-only data (what the game does not hold yet: ship roles, regions) sits under the sync block, edited by hand.

## Blender (headless)

Blender 5.3 is installed on the owner's Mac (`/Applications/Blender.app`, Homebrew cask; `blender` is also in `/opt/homebrew/bin`). It is not installed on the desktop PC: install it there, and `tools/blender.sh` finds it on the PATH or through `BLENDER=/path/to/blender`. There is no window and no MCP server: Claude drives it from Bash through `tools/blender.sh`, which runs `blender --background --factory-startup --python-exit-code 1` (a Python error fails the command).

- `tools/blender.sh script.py [args]` runs a script (read `args` after `--` in `sys.argv`); `tools/blender.sh -e 'print(1)'` runs one expression.
- Typical use: build or load a scene with `bpy`, render with `bpy.ops.render.render(write_still=True)` and export (for example glTF with `bpy.ops.export_scene.gltf`). Cycles on the CPU (`scene.cycles.device='CPU'`) renders with materials; Workbench is fast but ignores material colours.
- Keep scratch scripts and renders in the scratchpad, not in the repo. Anything meant for the game goes through the owner first, because the game is a single `index.html` with no assets folder.
